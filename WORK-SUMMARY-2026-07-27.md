## 1. Почему у бота «не было инструментов»

Причин три, и они накладывались друг на друга.

### Три слоя урезания инструментов

В логе всё видно по строкам `[agents/tool-policy]`:

| Слой | Что делает | Как чинится |
|---|---|---|
| `sandbox tools.deny` | по умолчанию режет `cron, gateway, nodes` | переопределяется `tools.sandbox.tools.deny` |
| `sandbox tools.allow` | **белый список** `alsoAllow` — всё вне его вырезается | добавить нужные инструменты |
| `gateway sender owner-only` | `cron` доступен **только владельцу** | владелец = `commands.ownerAllowFrom` |

Было разрешено только `["telegram","google-workspace","browser-use"]`, из-за чего
вырезались 23 инструмента, включая `web_search`, `web_fetch`, `memory_search`.
Добавлено: `web_search, web_fetch, tavily_search, tavily_extract, memory_search,
memory_get, memory_list, memory_add, pdf, cron`. Запрещёнными оставлены
`gateway, nodes` — управление службой и узлами боту не нужно.

⚠️ **Ловушка проверки.** Третий слой (owner-only) означает, что `cron` не виден
из CLI (`openclaw agent`) — там нет личности владельца. Консольный тест даёт
**ложноотрицательный** результат, проверять только реальным сообщением в Telegram.

### Песочница не имеет сети — `curl` там бесполезен

Контейнер агента создаётся с `NetworkMode: none`. Это защита по замыслу.

Разница, которая всех путала: в переписке с владельцем `curl` работает, потому
что `tools.elevated` выполняет команды **на хосте**; в задачах по расписанию этих
прав нет → exec уходит в песочницу без сети.

Замена — инструмент `web_fetch` (выполняется на хосте, проверен на example.com).

Попутно сделано, но **цели не достигло** (оставлено как безвредное):
образ песочницы пересобран с `curl`, демону Docker прописан рабочий DNS
(`/etc/docker/daemon.json`, `1.1.1.1`) — контейнерам доставался DNS провайдера,
который изнутри не отвечает. Для сборки образов полезно, для песочницы — нет.

### Доставка в cron-задачах

Инструмент `message` в песочнице закрыт, но отправлять и не нужно: у задачи
настроено `announce -> telegram`, итоговый ответ уходит владельцу автоматически.
Без этого знания бот извинялся «не могу отправить», хотя сообщение доставлялось.

## 2. Веб-поиск: работает Brave, не Tavily

| Провайдер | Напрямую из Москвы | Через Tor | Итог |
|---|---|---|---|
| **Tavily** | 403 (гео-блок) | 200 | плагин **игнорирует** прокси → выключен |
| **Brave** | **200** | 200 | включён, прокси не нужен |

Старый ключ Brave был мёртв (`422 SUBSCRIPTION_TOKEN_INVALID`, 17 символов).
Владелец выдал новый (31 символ, префикс `BSA`, бесплатный тариф 2000 запросов/мес).

⚠️ **Куда класть ключ.** Не в `env.BRAVE_API_KEY` и не в
`plugins.entries.brave.config.apiKey` — схема отвергает (`must not have
additional properties`), старт падает с `status=78/CONFIG`. Правильно:

```json
plugins.entries.brave.config.webSearch = {"apiKey": "…", "mode": "web"}
tools.web.search = {"enabled": true, "provider": "brave", "maxResults": 5, "timeoutSeconds": 30}
```

Без секции `tools.web.search` инструмент отвечает «web_search is disabled or no
provider is available», даже когда плагин включён.

Tavily перенаправить через redsocks нельзя: живёт на плавающих адресах AWS,
задело бы посторонний трафик.

## 3. Codex: заработал на подписке Plus (было — гео-блок + чужой ключ)

**Симптом:** `openai/gpt-5.5` падает с «You've reached your Codex subscription
usage limit». В личном кабинете ChatGPT при этом **99% недельного лимита не
тронуто** — формулировка вводит в заблуждение.

**Доказано измерением** (запрос к `https://chatgpt.com/backend-api/codex/responses`
с валидным токеном):

| Маршрут | Ответ |
|---|---|
| напрямую | **403**, страница блокировки Cloudflare по региону |
| через privoxy | **400 `Store must be set to false`** — штатная валидация API |

Значит авторизация и квота в порядке, ходить надо через Tor — а openclaw ходит
мимо и показывает 403 как «лимит».

**Что перепробовано и не помогло:**
- `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` в systemd drop-in шлюза;
- те же переменные перед CLI-командой входа (из-за этого падал и обмен OAuth-кода:
  `unsupported_country_region_territory`);
- `models.providers.openai.request.proxy = {mode: explicit-proxy, url: …}` —
  принимается, но на путь Codex не влияет. Для `openai-codex` overlay вообще
  невозможен: «custom model providers must declare baseUrl/models» → старт падает;
- у плагина `codex` настройки прокси в схеме **нет**.

**РЕШЕНО (в тот же день).** Помогли две правки, по отдельности бесполезные:

1. **Прозрачное перенаправление в Tor** — как для Telegram: `iptables -t nat
   REDIRECT` адресов chatgpt.com на redsocks. **Плюс закрытие IPv6**: у VPS есть
   глобальный адрес, у chatgpt.com — AAAA, и соединение уходило по IPv6 мимо
   правил v4. `ip6tables REJECT --reject-with tcp-reset` на `2a06:98c1::/32`
   даёт мгновенный откат на IPv4.
2. **Профиль подписки под именем `openai:manual`.** Путь Codex жёстко ищет
   профиль с этим id — а там лежал мёртвый платёжный ключ. Его 429
   `insufficient_quota` openclaw и переводил как «исчерпан лимит подписки».
   Под этот id положена копия OAuth-профиля подписки.

Проверка: модель представляется как «Codex на базе GPT-5». `gpt-5.5` вернулся
первым в цепочку резервных. Правила сохранены через `netfilter-persistent`,
адреса обновляет `codex-tor-route.sh` (cron `17 * * * *`).

**Приём, который следовало применить раньше:** `tcpdump` по SYN-пакетам во время
запроса. Пустой вывод показал, что openclaw **не делает сетевого запроса вообще**
— и сразу отсёк все гипотезы про прокси, на которые ушёл час.

**Итоговая цепочка:** primary `minimax/MiniMax-M2.7`, fallback `openai/gpt-5.5`
(подписка Plus) → `openrouter/google/gemini-2.5-flash` → `gonka/Qwen3-235B`.
Обе cron-задачи переведены на MiniMax — им хватает, а лимит подписки экономится
для диалогов.

⚠️ Платёжный ключ `sk-proj-…` мёртв (`429 insufficient_quota`) и **удалён** из
хранилища. ChatGPT Plus его не покрывает — это отдельный продукт с отдельной
оплатой.

## 4. Повторяющиеся задачи

**Было:** инструмент `cron` запрещён в песочнице. На просьбу «напоминай каждый
вторник» бот складывал инструкцию в `emmbase/inbox/` — и она висела, пока её не
разберёт Claude. Со стороны выглядело как «принял к исполнению».

Плюс в первом тесте бот **перепутал день**: просили вторник, записал среду.

**Стало:** `cron` разрешён (владельцу). В `workspace/TOOLS.md` записаны правила:
проговаривать день недели и время вслух перед созданием, не трогать чужие задачи,
«Утренний-прогноз» и `pattern-analysis-weekly` не менять никогда, при неудаче
говорить прямо. После правила бот во втором тесте сам исправился на вторник.

**Не проверено до конца:** создание задачи реальным сообщением в Telegram —
из CLI не проверяется (owner-only, см. раздел 1).

## 5. Бот замолчал из-за защиты от циклических падений

Эксперименты с конфигом прокси уронили шлюз 4 раза подряд → сработал
`restart-loop breaker`: служба работает, но **канал Telegram не поднимается
автоматически** («channel autostart suppressed by crash-loop breaker»).

Признаки, сбивающие с толку: служба `active`, очередь пуста, сеть исправна —
formально всё здорово, просто канал выключен намеренно.

Лечение: дождаться окна (5 мин без падений) и сделать один чистый рестарт;
`openclaw channels status` показывает причину в поле `error:`.

**Закрыто:** в `telegram-watchdog.sh` добавлен четвёртый детектор — признак
`autostart suppressed` в журнале за 15 минут. Проверен подстановкой журнала:
срабатывает на подавленный канал, молчит на чистом.
